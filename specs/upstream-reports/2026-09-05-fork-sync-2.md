## Sync Mechanics

`make upstream-sync-fork-main` **cherry-picked cleanly and then failed its post-apply checks**, on
`fork-ownership-coverage-check`. Per the skill's standing warning, `CHERRY_PICK_HEAD` was checked before
deciding state rather than assuming a rollback: there was no cherry-pick in progress, `HEAD` had
**advanced** to the applied commit, and the tree was clean — so this run neither rolled back (batch 227)
nor left a conflict staged (batch 226). That is a **third** distinct failure posture from the same
script in three cycles, which is the reason the check exists.

Recovery kept the script in charge of the state rather than hand-applying:

1. `git reset --hard e1e7744918894c05` to drop the applied commit, re-applying the manifest fix as its
   own commit **below** the sync (`ea123934b56`).
2. `git cherry-pick --ff afe31a0c3a9` to restore the fork commit.
3. `make upstream-sync-fork-main ROLLING_CONTINUE=1`.

Step 3 was possible because `activeForkSyncIsApplied()` accepts a `git cherry` patch-id equivalent, not
only a literal ancestor — so a re-applied copy under a new SHA satisfies the continue guard. The script
then re-ran all three checks, advanced `integratedForkHead` to `afe31a0c3a9`, cleared `activeForkSync`,
and wrote its own `appendHistory` entry. **No hand-advanced state this cycle** — the first cycle in four
where the recorded state is entirely script-written.

## The Masked Gate — `scripts/spec-citation-check.sh`

`fork-ownership-coverage-check` failed with one hard error:

```
Ownership manifest does not cover 1 fork files:
scripts/spec-citation-check.sh
```

The file landed on `main` with **#931 on 2026-09-04** and never got a manifest row. It is uncovered at
the previous `integratedForkHead` (`3bb200f4364`) as well, so the gap is **pre-existing, not caused by
this cycle's cherry-pick**.

**Why it stayed hidden for two cycles:** the check is a _post-apply_ step. Batches 226 and 227 both threw
during cherry-pick — on conflicts — and never reached it. This cycle's single commit applied cleanly, so
the checks ran for the first time since #931 merged and the gap surfaced immediately. The lesson
generalises: **a fork sync that throws early silently skips its own post-apply gates, so a clean cycle
can surface findings that belong to an earlier one.** Do not read a first-time gate failure as caused by
the commits currently in flight — check the previous baseline, as was done here.

Fixed in `ea123934b56` by adding the script to `release-ci-and-infrastructure` `owned_paths`, beside the
other fork tooling. `make fork-ownership-coverage-check` now exits **0**.

### Correction to the previous report

The 2026-09-05 report attributed this check's non-zero exit to its ~740 advisory
"`<path>` is covered only by `<broad-glob>`" lines and called it deliberately-tolerated noise. That
diagnosis was wrong. Those advisories are emitted through `console.warn` and, absent
`--strict-broad-coverage`, never set an exit code — **proven** by the post-fix run, which still prints
all 740 of them and exits 0. The uncovered file was the sole cause of the failure the whole time.

The genuinely-tolerated warning is a different one, and it remains:

```
Ownership manifest last_verified_fork_head 690fd44e12c is behind afe31a0c3a9; 1804 files changed since manifest verification.
```

This is a warning by construction (`manifestHeadValidation({ warnings: [...] })`) and is left alone
deliberately. Bumping `last_verified_fork_head` would assert a verification of 1804 files that has not
been performed; it is its own piece of work, not a rebase side effect.

### Related finding — the gate itself runs nowhere

`scripts/spec-citation-check.sh` is invoked only by `make spec-citation-check`. `grep -rn` across
`.github/` returns nothing, and it is not reachable transitively through any umbrella script (unlike the
branding scripts, which reach CI via `gallery-branding-check.sh`). It is a **Makefile-only gate**: real,
useful, and never run by CI. Run manually here — `all spec citations across 4 source tree(s) resolve`.
Wiring it into a workflow is a change for `main`, not for the rolling branch, so it is **reported, not

**2. The rolling copy of #1022 lost its `(#1022)` subject suffix.** Fixing (1) unmasked the next check
in the same chain: `make upstream-rolling-final-check` now reports

```
Missing fork commit subject in rebase branch: fix(revert): delete Gallery's own workflow plugin so upstream Immich can boot (#1022)
```

`origin/main` has it as `3baa2a35f32` with the `(#1022)` suffix; rolling carries it as `f84bbc90698`
**without** the suffix, from a hand-applied cherry-pick in an earlier cycle. `findMissingSubjectMatches`
matches on either a whitespace-normalised subject or a shared `(#N)`, and `normalizeSubject` only
collapses whitespace — so a dropped suffix defeats both arms.

**It is cosmetic, and that was verified rather than assumed.** The two commits are **patch-identical**
(`git patch-id --stable` → `0beede5422b` on both sides), and the substance is present in the tree:
`scripts/revert-to-immich.sql` §6b deletes the `gallery-core` plugin row under its `to_regclass` guard.
The real gate for that content, `gallery-revert-to-immich-validation`, ran green this cycle.

**Not fixed here, deliberately.** `f84bbc90698` sits **166 commits deep**, so rewording it rewrites 166
SHAs — which would invalidate the ten CI runs already in flight and cost a second full dispatch, to turn
a local-only command green. `rolling-final-check` is in **no workflow** (`grep -rn rolling-final-check
.github/` is empty), exactly like `fork-ownership-coverage-check`.

The right moment is **the next cycle that consumes an upstream batch**, since `git rebase` will already
be rewriting every one of those SHAs; restoring the suffix there is nearly free. Left unfixed it is not
harmless — it is a standing false positive on a check whose whole job is to prove no fork commit was
dropped, and this cycle is the second demonstration that a stale failure at the head of a check chain
hides whatever sits behind it.

### The one red job — `Medium Tests (Server)`

`PostgresError: sorry, too many clients already` (PG **53300**). **179 of 180 test files passed**; every
failure is inside the fork-only `test/medium/specs/services/face-repair.service.spec.ts`.

This is the known, documented, still-unfixed rolling-only medium-test connection exhaustion. It was
**not** waved through as a flake — it failed on **all three attempts** (initial + two re-runs), so
re-running exhausted its usefulness and it was characterised instead. Four independent pieces of
evidence, in increasing order of decisiveness:

1. **Identical-tree divergence.** `server/` is **byte-identical** to `1945a99e7ce`, where this same job
   passed on the previous cycle's first dispatch. The same bytes both pass and fail, so no code in this
   cycle can be the cause. (`git rev-parse 1945a99e7ce:server` == `git rev-parse HEAD:server`.)
2. **The error is a resource limit, not an assertion.** Nothing asserts a wrong value; Postgres refuses
   new connections. The other `PostgresError` lines in the log (`duplicate key …`, `avg(vector) does not
exist`) are expected negative-path output present in passing runs too.
3. **The failure set shifts on every attempt** — **3 → 2 → 4** failing tests across the three runs,
   always the same file, always 179/180 files passing. A deterministic code defect does not move.
4. **It passes 20/20 in local isolation.** `npx vitest --config test/vitest.config.medium.mjs --run
test/medium/specs/services/face-repair.service.spec.ts` → `Test Files 1 passed, Tests 20 passed`,
   9.9s. The spec is sound; it only fails when sharing a Postgres with 179 other spec files.

**Be precise about the frequency.** Three-for-three is not "intermittent" on this dispatch — on this
runner, today, it reproduces every time. What is intermittent is _across dispatches_: the byte-identical
tree went green on the previous cycle's first attempt, and `test.yml` on this branch reads success ×4
with a single earlier failure on 2026-08-19. The honest statement is that the suite now sits close
enough to the container's connection ceiling that whether it crosses depends on the runner, not on the
code — which is exactly the documented mechanism (~160 of ~165 medium specs never `.destroy()` their
pool, and `globalSetup.ts` sets no `max_connections`). The fork's medium suite is the reason rolling
crosses it where `main` does not: upstream 64 → `main` 161 → rolling 180 spec files.

**Recommendation unchanged: PROCEED**, but with a sharper follow-up than "watch it". The condition is
pre-existing and provably unrelated to the synced commit, yet 3/3 is a real deterioration from the
previous cycle's clean pass and the trend is one-directional — every cycle that adds a medium spec
pushes rolling further over the ceiling. The one-line first fix is already identified: add
`-c max_connections=200` to `globalSetup.ts`'s `.withCommand([...])`. **It does not belong in a rebase
cycle** — touching `server/` forfeits the byte-identical-to-a-green-tree property that makes the triage
above possible — so it wants its own PR on `main`.
