# Storage Template on S3 — Design

Supersedes the "storage template is a no-op on S3" decision recorded in `2026-03-02-s3-storage-design.md` ("S3 moves: No physical copy+delete"), the skip guards of `2026-04-19-storage-template-s3-compat-design.md`, and the "S3 never writes to library/" exclusion of `2026-04-22-s3-orphan-cleanup-user-delete-design.md`.

## Problem

With `IMMICH_STORAGE_BACKEND=s3`, the storage template did nothing. `StorageTemplateService.moveAsset` returned early for every relative (S3) `originalPath`, and `StorageCore.moveFile` returned early for any relative `oldPath`, so an S3 upload stayed at `upload/<userId>/ab/cd/<assetId>.<ext>` forever, and the Migration job ("migrate thumbnails to the latest folder structure") never touched S3 thumbnails or encoded videos. The S3 docs said the opposite.

## Owner decisions (2026-10-20, decision 1 revised 2026-10-21)

1. **No new toggle; after an upgrade with S3 files, one manual run first** (revised 2026-10-21). The existing "Enable storage template" switch governs S3 too, and an S3 upload moves to its template path after metadata extraction, as on disk. The exception is an install that upgrades with originals already in S3 and the template enabled. The template did nothing in its bucket before, so moving its new uploads the moment it upgrades would surprise its admin. There, S3 files keep their upload keys until an admin finishes one Storage Template Migration by hand; that run moves the existing objects, and new uploads move automatically from then on. Fresh installs, installs whose template was off at upgrade (turning it on later is the admin's own choice) and disk files keep the automatic move. The 2026-10-20 version of this decision had those upgraded installs start moving new uploads at once, like the rest. The owner chose this narrow rule, and chose a warning in the startup log as the admin's only notice over a notice on the settings page (the cheaper option; a notice may come later). Mechanism: [One manual run first after an upgrade with S3 files](#one-manual-run-first-after-an-upgrade-with-s3-files).
2. **Verify like Immich does on disk.** Upstream's disk move renames without checking anything and only verifies (size, then SHA-1 when `storageTemplate.hashVerificationEnabled`) a file it has to trust without having moved it itself: one an interrupted move left at its new location. An S3 server-side copy is treated as the rename, plus the size check a copy needs (a `HeadObject`): no read-back of the object. The SHA-1 check runs only in the interrupted-move recovery path, as upstream.
3. **Derivatives move on a manual run.** Starting the Storage Template Migration job by hand (the admin Jobs page) also re-paths the S3-stored thumbnails, previews, full-size images, encoded videos and person thumbnails, the work upstream's Migration job does for disk. The Migration job itself now handles S3 files as well.

## Why a copy

S3 general-purpose buckets have no rename. `RenameObject` exists only for S3 Express One Zone directory buckets, and MinIO, Garage, R2 and B2 have none. A move is `CopyObject` (server-side: no bytes pass through Gallery, nothing leaves the bucket) and `DeleteObject`. `CopyObject` stops at 5 GiB, so larger objects use a multipart copy (`UploadPartCopy`).

## Design

### Namespaces: a file stays in the backend that holds it

A stored path is a disk file when absolute and an S3 key when relative (`isDiskPath`). `<mediaLocation>/<key>` on disk and `<key>` on S3 are the same logical location: the storage migration maps one onto the other (`StorageMigrationService.computeTargetPath`). The template never moves a file between backends. It renders the destination in the namespace of the original, and the mover reads any new path in the namespace of the file it moves.

One function maps a path to its key: `toS3Key(path, mediaLocation)` in `src/gallery/utils/s3-key.ts`. A key stays as it is, a disk path under the media location loses that prefix (`path.relative`, so `//` and `..` segments are normalised and a folder named `..hidden` still counts as inside), and any other disk path has no key (null). The mover, the destination check and the storage migration's `computeTargetPath` all use it; the migration keeps its old fallback for a path outside the media location (an external library original keys as its whole path without the leading `/`). `isInStorageFolder(path, folder, mediaLocation)` beside it answers "is this under `<folder>/`" for disk paths and keys alike. The module imports neither `storage.core.ts` nor a service; the media location is passed in.

**Backend registry.** The process's backends (`diskBackend`, `s3Backend`, `writeBackendType`, `getWriteBackend()`, `backendFor()`) live in `storageBackends` (`src/gallery/utils/storage-backends.ts`), a leaf module set once by `StorageService.onBootstrap`. `StorageService` keeps its four static methods as one-line delegates, so existing callers and `vi.spyOn(StorageService, …)` work unchanged. The mover and the destination check read the registry directly: with the backends as private statics on a service that extends `BaseService`, the mover could only reach them through a lazy `import()` of `storage.service.ts`, which hid a real cycle (`storage.core` → mover → `storage.service` → `base.service` → `storage.core`). The three older lazy imports of `storage.service.ts` (`backend-media-server.ts`, `BaseService.syncUsage`, `machine-learning.repository.ts`) are left as they are.

### Backend primitives (`src/interfaces/storage-backend.interface.ts`)

- `copy(fromKey, toKey)`: S3 `CopyObject` up to 5 GiB, multipart `UploadPartCopy` above (content type carried over from `HeadObject`, upload aborted when a part or the completion fails). `CopySource` is URL-encoded per path segment: template names hold spaces, Unicode and the `+N` duplicate suffix, which S3 would otherwise read as a space.
  - **Storage class.** A copy is written in `STANDARD` unless told otherwise, which would undo a lifecycle rule's transition (and, for Standard-IA, bill the original's minimum storage duration on delete). The source's class is sent when it is one of the SDK's `StorageClass` values other than `STANDARD`. A provider's tier name is not: MinIO reports an ILM-transitioned object's tier (`WARM-TIER`) in `HeadObject` and rejects it on `CopyObject` and `CreateMultipartUpload` with `InvalidStorageClass`, so such a copy lands in the default class and the provider's own rule transitions it again once it is old enough. An object in an archive class (Glacier Flexible Retrieval, Deep Archive) cannot be copied until restored; its move fails with `InvalidObjectState`, logged on every run.
  - **No `UploadPartCopy`.** Storj's gateway answers `UploadPartCopy` with 501 `NotImplemented`, and its `CopyObject` has no 5 GiB limit, so a 501 anywhere in the multipart path falls back to one `CopyObject` (an upload already created is aborted first). Any other error is the copy's.
  - **Abandoned parts.** The abort covers failures Gallery sees. A process stopped mid-copy leaves its parts, invisible in a listing and billed, which only a bucket lifecycle rule (`AbortIncompleteMultipartUpload`) removes: the same exposure an interrupted multipart upload already had. The S3 docs recommend the rule.
  - **Disk.** `mkdir` + `copyFile`, then the source's atime and mtime, as upstream's disk move keeps them (`rename`, or `utimes` after its cross-device copy). The interface keeps `copy` and `stat` generic, but the mover is S3-only (below), so nothing calls the disk `copy` today; the storage migration uses the disk `stat`.
- `stat(key)`: `{ size }` (`HeadObject` `ContentLength` on S3).
- `put(key, source)` on disk writes `.<uuid>.tmp` beside the target (a fixed-length name: one derived from the target's could exceed the 255-byte file name limit the target itself fits in) and renames it into place, removing the temp file on failure. An S3 upload was already atomic: the object appears only on a completed `PutObject` or `CompleteMultipartUpload`. So an interrupted write never leaves a partial file at the target, which the storage migration's size check (below) would otherwise refuse on every retry. There is no fsync before the rename, so a host crash right after a write can still leave a short file. A process killed mid-write leaves the temp file instead, which nothing reads and no job cleans up.

### The mover (`src/gallery/utils/s3-file-move.ts`)

`StorageCore.moveFile` hands every request that is not disk-to-disk to `moveS3File` (one call; the old early return is gone). Keys are written only while S3 is configured, so the mover is S3-only: without an S3 backend it logs `Unable to move <id>: <old> => <new> needs S3, which is not configured` and returns before reading or writing a `move_history` row, leaving the file (and its sidecar) where it is, as before this work.

| `oldPath` | `newPath`                    | Result                                                                                                       |
| --------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------ |
| key       | key                          | move inside S3                                                                                               |
| key       | disk path under media loc.   | the path becomes its key (`thumbs/…` for `/data/thumbs/…`); move inside S3. Derivative migration takes this. |
| key       | disk path outside media loc. | refused with a warning                                                                                       |
| disk path | key                          | the key becomes `<mediaLocation>/<key>`; upstream's disk move. A disk sidecar of an S3 original takes this.  |

The last row exists for a disk sidecar of an S3 original, which a storage migration leaves when it runs without sidecars (or its sidecar job fails). The template sends the sidecar to `<new key>.xmp`, in its original's namespace. Upstream's disk move cannot take that key: it would create the folder and rename relative to the working directory, then save a relative path, which every reader takes for an S3 key.

The move follows upstream's `moveFile` step for step, `move_history` included, so the next attempt finishes an interrupted one. Upstream's `moveFile` returns before any of this when `oldPath === newPath`.

0. **A sidecar waits for its original.** The template sends the sidecar to `<new original>.xmp` right after the original's move, whether or not that move finished. A move that stops without throwing (copy error, size mismatch, missing asset info, file at neither location, failed verification) keeps its `Original` row and leaves the original where it was; its destination name is still free, so the next asset rendered to that name takes it, and that asset's sidecar overwrites this one. While the entity has an `Original` row, the mover does not move its sidecar (warning logged): a key sidecar, or a disk sidecar of an S3 original. A disk sidecar of a disk original never reaches the mover and keeps upstream's behaviour. The reverse case, a sidecar whose own move failed after its original moved on, stays at `<old name>.xmp` while that name is free for the next asset; so a fresh sidecar move also refuses a destination that already exists (warning logged, no row), since the template probes only the original's destination and a copy overwrites.
1. **Find the entity's `move_history` row** (`startOrResumeMove`, one early return per case):
   - No row: a fresh move, created here (a sidecar first refuses a taken destination, as in step 0).
   - Disk paths while the file is a key: a disk move of this file stopped before deleting its row (a rename error, a mismatch after a cross-device copy, a crash), then a storage migration moved the file into S3. Replaced by this move; upstream's recovery would look the disk paths up in S3, find neither, and give up on every run.
   - `oldPath` is not the database's path, and the database's path exists: the database has moved on. An earlier move saved its new path, then stopped (a crash) before deleting the row, and the template now renders another destination (with the same one, `moveFile` returns before this). The row is replaced and the move starts from the database's path. Upstream's recovery would copy the row's `oldPath` over the destination, orphaning the database's file, which for a sidecar may have been rewritten since. The row's `oldPath` is not deleted either: an admin may have removed that orphan by hand, and its name may since have been given to another asset. It stays an orphan.
   - Otherwise upstream's recovery of this file's own unfinished move (the copy failed, the size differed, asset info was missing, or a crash before saving): file at old, at new (verify size and, if enabled, SHA-1 by staging the object), or at neither (give up with upstream's warning). This includes a database path that is gone: an interrupted recovery may have moved the row on to a file the database never pointed at.
2. `copy(old, new)`.
3. `stat(new).size` against the asset's `fileSizeInByte` (or `stat(old)` for a derivative or sidecar), through `hasExpectedSize`, the size half of upstream's `verifyNewPathContentsMatchesExpected`, which the recovery's verification shares; a mismatch logs upstream's `Unable to complete move. File size mismatch: …`. On mismatch stop; the row stays for the next attempt. Only an original's copy is deleted: its destination was picked as free under the template lock, so the object there is this copy. A derivative's key is fixed per asset and a sidecar's is not probed, so another job (a regenerated thumbnail) may have just written it; deleting it would delete that job's file. The next attempt redoes the copy over it.
4. Save the new path (upstream's `savePath`).
5. Delete the old key. A failure is a warning: the object is orphaned, the asset is fine.
6. Delete the row.

The database moves before the old key is deleted, the reverse of upstream's cross-device disk fallback: a crash between 4 and 5 leaves an extra object, never an asset whose key is missing. Without asset info (derivatives) a file found at the new location cannot be compared and is accepted; upstream would `stat` the missing old file and throw on every retry.

Crash windows, each leaving an orphaned object as upstream's cross-device copy fallback does on disk:

- **Between 2 and 4** (copied, not saved): on the next run the template sees its own copy occupying the destination and picks `+1`; recovery copies the still-present old key there, and the first copy is never referenced. Treating "the destination this entity's own row targets" as free would avoid it, but only safely after proving the object there is this asset's copy (size and checksum): if the crash came before the copy, another asset may have taken that name since. Not done; the window is the length of one `HeadObject` and one `UPDATE`.
- **Between 4 and 6** (saved; old key or row not yet deleted): the old key may stay behind, and the row does. The next run with the same template finds the asset in place and returns before reading the row, so the row stays until the asset moves again, when step 1 replaces it as outdated and its old key stays an orphan. Until then step 0 keeps the asset's sidecar where it is: still referenced and served, just not templated. Workaround, while no template migration runs: `DELETE FROM move_history m USING asset a WHERE m."pathType" = 'original' AND m."entityId" = a.id AND m."newPath" = a."originalPath"` (rows of moves whose save went through), then run the template migration again.

A `move_history` row left by an interrupted key move, followed by an S3-to-disk storage migration, holds keys while the file is on disk. Upstream's disk recovery then finds the file at neither key and gives up on every run for that entity (the reverse, a disk row for a key file, is handled). Workaround, as for upstream's stale rows: `DELETE FROM move_history WHERE "oldPath" NOT LIKE '/%'` while no template migration runs.

### Storage template seams (`src/gallery/utils/storage-template-s3.ts`)

`StorageTemplateService.getTemplatePath` makes two calls into the fork module and otherwise runs upstream's code (album lookups, `+N` duplicate handling, the path-traversal guard):

- `getTemplateLibraryRoot(originalPath, user)`: upstream's `<mediaLocation>/library/<label>` for a disk original, the key `library/<label>` for an S3 original (`<label>` is the storage label, or the user id without one), always with a trailing `/`. Upstream's guard is `fullPath.startsWith(rootPath)`, and without the slash `library/admin` also admits `library/admin2/…`: make, model and lens are rendered unsanitized, so EXIF `../admin2` escapes into another user's folder, which user deletion then removes with that user. The slash closes the gap on disk too.
- `isTemplateDestinationTaken(destination, storageRepository, logger)` (the service's logger, so its warning follows the log format and carries the job's correlation id): upstream's disk check alone when S3 is not configured. With S3 configured a destination is taken when either backend holds it. Otherwise a disk asset at `/data/library/admin/2024/IMG_1.jpg` and an S3 asset templated to `library/admin/2024/IMG_1.jpg` would collide at the next storage migration, which would refuse the second asset's target as a size mismatch or, when the sizes happen to match, point it at the first one's file.
  - The S3 check failing is fatal only for an S3 destination: the error reaches `getTemplatePath`'s catch, which keeps the original path, so the asset is not moved this run. For a disk destination it is logged and the key counts as free: upstream never asked S3 about a disk destination, and an S3 outage must not stop disk templating. The storage migration's size check is the backstop for the collision this can let through.

`StorageCore.isAndroidMotionPath` is one call into the fork's `isInStorageFolder`, which reads disk paths and keys alike, so it also recognises `encoded-video/` keys: an Android embedded motion video on S3 lives at `encoded-video/<owner>/…-MP.mp4` and, as on disk, is not templated. This also fixes `includeEmbeddedVideos` for S3 downloads. Its disk answer now differs from upstream's prefix check only on paths Immich never writes (every writer uses `join`): the folder itself, a sibling such as `<mediaLocation>/encoded-videos/`, and a path not in normal form, such as one with a doubled `/`. `getBaseFolder` stays upstream's: every other caller needs the absolute disk folder.

### Derivative migration on a manual template run

A fork service (`StorageTemplateS3Service`) listens for `QueueStart` (emitted only when an admin starts a queue by hand). For the Storage Template Migration queue, with S3 configured and the template enabled, it queues one job (`S3FileMigrationQueueAll`) on the Migration queue that streams the assets holding a non-edited derivative under a key, and the people whose thumbnail is a key, and queues upstream's `AssetFileMigration` / `PersonFileMigration` for them. Those handlers run upstream's `moveAssetImage` / `moveAssetVideo` / `movePersonFile`, which reach the mover through `moveFile`. Disk derivatives are left to upstream's Migration job, as before.

Nothing is queued while the Migration queue has an active job. Upstream refuses to start the Migration queue while it is active ("Job is already running") and the per-file jobs have no deduplication, so a second set queued over a running one would run two jobs for one entity at once (the queue's default concurrency is 5): the loser fails on the `move_history` row or a missing key, and the database still points at an existing key. The test is upstream's (active jobs only), so a paused queue holding waiting jobs still lets a second set in, as it does for upstream's own Migration start.

### One manual run first after an upgrade with S3 files

Decision 1's exception, in three parts: a state decided once, cleared by the first manual run, and read by a gate on the per-asset job.

**State.** `SystemMetadataKey.StorageTemplateS3State` (`storage-template-s3-state` in `system_metadata`): `{ pending: boolean; decidedAt: string; clearedAt?: string }`. An absent row reads as not pending.

**Decided once, before the job workers start.** `StorageTemplateS3Service.onBootstrap` runs on `AppBootstrap` at `BootstrapEventPriority.JobService - 1`, in the API and microservices workers. Without a row it takes `DatabaseLock.StorageTemplateMigration`, reads the row again inside the lock, and only if it is still absent saves `pending = storageTemplate.enabled && hasS3Originals()`, where `StorageMigrationRepository.hasS3Originals` asks whether any asset, trashed or not, has an `originalPath` not starting with `/` (a `LIMIT 1` query; its cost is below). With a row it never decides again, so turning the template on later, or switching uploads to S3 later, never makes an install pending: both are the admin's own later choices, not something the upgrade did.

- The priority puts the decision before `QueueService` starts the queue workers at `JobService`: a per-asset job run first would read no row, which means not pending, and move.
- Both workers run it because either may start first, and the API worker's `AppBootstrap` (`onModuleInit`) completes before Nest listens: on a fresh install, an S3 upload accepted before the decision would make the install look like an upgrade.
- The first decision stands, and only one worker runs `hasS3Originals()`. Two workers starting together both find no row; the lock makes the second wait, and its re-read inside the lock finds the first one's row. Without the lock and the re-read the second would decide again, and if its query ran after the API worker, done deciding, had accepted an S3 upload, it would count that upload and save `pending: true` over a fresh install's `false`. The lock is the one `moveAsset` takes for each asset, so a template move running in another process delays the decision by at most that one move. Once a row exists, a start reads it before the lock and never takes the lock.
- **Cost on a large install without S3 originals.** `LIMIT 1` stops at the first match, and there is none, so the query reads the whole `asset` table: no index serves `originalPath NOT LIKE '/%'` (the `(originalPath, libraryId)` index cannot answer a negated pattern). That includes a disk-only install. Both workers' first start waits for the scan: one runs it, the other waits on the lock. It runs once per install, in one worker, and only with the template enabled (with it off, the `&&` skips the query).
- While pending, each worker logs a warning on every start naming the job and where to start it. It is the admin's only notice (decision 1).

**Cleared by the first successful manual run.** `StorageTemplateS3Service.onJobSuccess` (microservices only: `JobSuccess` is emitted in the worker that ran the job) saves `pending: false` and `clearedAt`, and logs it, when `StorageTemplateMigration` (the bulk job) returns `Success` while the state is pending. Only `QueueService.start` queues the bulk job, so only an admin starting the Storage Template Migration queue clears the state.

- With the template off the bulk job returns `Skipped`, and a run that throws emits `JobError`: neither clears.
- A file whose move fails inside the run is logged and does not fail the job, so a finished run clears the state with that file still at its key. The next manual run moves it, as on disk. This holds even when every S3 move in the run fails: `handleMigration` returns `Success`, each failure is logged, and the state clears with every S3 file where it was; uploads move automatically from then on. Clearing only after a run without failures would need upstream's `moveAsset` to report its failures to `handleMigration`, a change to upstream's code the fork avoids (rule 5 of `CLAUDE.md`).
- The per-asset jobs share the bulk job's queue, which runs one job at a time per worker. With one microservices worker, an upload made during the run is queued behind it and moves after the state is cleared. With several, another worker can run that upload's per-asset job during the run and skip it, while the run's stream, opened at its start, does not include it: that upload keeps its upload key until the next manual run. Not handled.

**The gate.** `isManualOnlyTemplateMove(asset, systemMetadataRepository)` in `src/gallery/utils/storage-template-s3.ts` returns false without reading anything when neither the original nor any of the asset's loaded files (the job loads its sidecar) is a key. Otherwise it reads the row and returns `pending`. The read is not cached, so a clear in one worker reaches every other worker without a restart.

- **Why it reads the state only for assets with S3 files.** The template always moved disk files, and upstream's job moves them after every upload; their behaviour must not depend on the bucket's history. Checking the paths first also keeps a disk-only install free of any extra query per upload.
- **Why a key sidecar holds back a disk original.** `moveAsset` moves the original and then its sidecar to `<new original>.xmp` in one call. Letting the automatic job move the original while the sidecar waits would split the two; the asset waits whole instead.

`StorageTemplateService.handleMigrationSingle`, the per-asset job (its only producer is `AssetMetadataExtracted`), checks the gate per part:

- **The asset, before reading its owner.** True returns `Skipped`, as upstream does with the template off, so `JobService.onDone` still queues thumbnail generation for an upload. A live photo whose still waits keeps its motion part where it is too.
- **A live photo's motion part, before its move.** True leaves the motion part where it is, and the job returns `Success` for the still it moved. The motion part is its own asset with its own path, and nothing keeps the two parts in one backend: Storage Migration moves file by file and leaves a file that fails on its old backend. Checking the still alone would move the S3 motion part of a disk still while pending. The manual run later moves the motion part next to the still, since its name and folder are rendered from the still.

The bulk job (`handleMigration`) does not call the gate: it is the manual run.

**Revert and downgrade.** `scripts/revert-to-immich.sql` deletes the row in step 0b with the other fork `system_metadata` keys. Step 0 refuses to run while any file is in S3, so a database that comes back to Gallery after a revert decides "not pending" on its first start. A downgrade to an earlier Gallery build keeps the row, which that build never reads; upgrading again finds it already decided.

**Release candidates.** RC images built from this branch before this rule moved S3 uploads automatically and wrote no row. An install that ran one decides on its first start after updating to an image with the rule, and with the template enabled and any original in S3 (under `upload/` or already moved to `library/`: both are keys) that decision is pending. Testers run Storage Template Migration once to clear it.

The unit specs of `StorageTemplateS3Service`, `storage-template-s3.ts` and `StorageTemplateService` cover the decision, the clear and both gates. The `template-s3-upgrade-pending` phase of the storage-migration E2E (`e2e/src/storage-migration.ts`) runs it against MinIO with a real decision: the harness starts from an empty database, whose first start decides "not pending", so `template-s3-upgrade-prepare` deletes the row and enables the template while originals are in S3, the workflow restarts the server, and `template-s3-upgrade-pending` asserts the restart decided `{pending: true}` with a fresh `decidedAt` and logged the warning, then that an upload waits at its upload key and the manual run moves it and clears the state. A medium spec (`server/test/medium/storage-migration.repository.spec.ts`) covers `hasS3Originals()` against Postgres (disk, key, trashed-key originals, and a key sidecar that does not count). The decision logs a line before it takes the lock, so a boot that waits on it (another process holding the template lock mid-move) or fails on the query (a `statement_timeout` shorter than the one-time scan) can be told apart; a failure stops the worker and is retried on the next start, and disabling the template skips the query. It does not default to "not pending" on error: that would bring back the automatic moves the rule exists to prevent.

### Accounting and cleanup

- `computePhysicalUsage` counts S3 `library/<label>/` (it already under-counted after a disk-to-S3 migration, which writes there).
- User deletion removes the S3 keys of the five folders upstream removes on disk (`library/<label>/`, and `upload/`, `profile/`, `thumbs/`, `encoded-video/` under the user id) whenever S3 is configured, whatever the write backend: objects stay in the bucket after a switch back to disk. `library/<label>/` is skipped, with a warning, while an asset of another owner has its original or one of its files under it. The label is an admin setting: it can change without a template migration, leaving the files under the old label, and the old label can then be given to another user, whose deletion would otherwise remove the first user's originals. The id-keyed prefixes cannot be shared. The disk library folder keeps upstream's unconditional removal, in upstream's lines. A failed prefix delete is logged and not retried: the same job deletes the user row, so nothing queues it again, and the objects are found only by hand.
- The storage migration no longer trusts an existing target blindly: it compares sizes and fails the file on a mismatch (logged with both paths) instead of re-pointing the asset. It does not delete the target after a failed `put`: the "target does not exist" check and the `put` are separate steps, so another writer may have created the target in between, and with both backends' writes atomic a failed `put` has nothing partial to remove. An existing target is usually this file's own copy: from a run of this migration that stopped before saving, or from a migration the other way with "delete source" off (the default, and the documented way back), stale if the source was rewritten in place since (a regenerated thumbnail or encoded video, a re-trim, a sidecar write). It can also be a partial or different file left by a build before atomic disk writes, by a host crash before a disk write was flushed (`put` does not fsync), or by a thumbnail or encoded video made for S3, which `MediaService` renders at the disk path a migration to disk targets and then uploads (`persistFile`), so a render that stopped or an upload that failed leaves it there; or, under `library/` only (every other name carries the entity's id), another asset's file: a template name given out by a build that checked disk only, or while S3 could not be asked. Overwriting is no safer than adopting: it could destroy another asset's file, or one a job just wrote to the target. An equal size is not proof (a sidecar rewritten at the same length passes); comparing sidecar bytes was considered and not done. The docs tell the admin to look before acting: a leftover of the same asset is deleted and the migration rerun; another asset's file stays, and the failing asset stays on its current backend.

## What users see

- A new S3 upload is `PUT` to `upload/…`, then after metadata extraction copied to `library/…` and deleted from `upload/…`: the same two steps disk takes.
- On an install that upgraded with originals in S3 and the template enabled, the second step waits for the first manual Storage Template Migration. Uploads work as before the upgrade: the object stays at `upload/…` and is served, thumbnailed and transcoded from there. Every start logs a warning in each worker (`The storage template does not move files in S3 until an admin runs Storage Template Migration from Administration > Job Queues; …`). The manual run moves the waiting uploads with the existing objects, logs `Storage template migration finished: new uploads in S3 now move to their template path`, and the warning stops. Assets stored entirely on disk keep moving after each upload throughout, except the disk motion part of a live photo whose still is in S3, which waits with the still.
- Requests, made serially: about five per moved original (`HeadObject` probe of the destination, `HeadObject` + `CopyObject`, `HeadObject` of the copy, `DeleteObject`) and about five per sidecar (`HeadObject` + `CopyObject`, `HeadObject` of both keys, `DeleteObject`), plus one `HeadObject` per extra `+N` candidate. A multipart copy adds `CreateMultipartUpload`, one `UploadPartCopy` per part and `CompleteMultipartUpload`. Later runs make none for assets already in place.
- `+N` probing is quadratic. Upstream's loop probes `name`, `name+1`, … until one is free, so the k-th asset rendered to one name costs k probes and n such assets about n²/2. On disk a probe is a local `stat`; on S3 it is a `HeadObject`, and with S3 configured a disk destination costs one too. Templates that render many files to one name (`{{filename}}` without a date folder, camera counters that wrap) pay for it. Not changed: avoiding it means replacing upstream's loop (listing the prefix once, or caching the highest suffix).
- Versioned buckets keep a noncurrent version of every moved object until a lifecycle rule expires it. Object Lock on AWS and MinIO requires versioning, so the delete adds a delete marker and the locked object stays as a noncurrent version until its retention ends; providers whose lock refuses deletes outright (R2 bucket locks, Wasabi compliance mode) leave the old key in place, logged with its key.
- A job that read an asset's old key just before the move and opens it after fails with `NoSuchKey`, the same race upstream has with `rename` on disk, with a wider window. A presigned URL issued for the old key stops working.

## Layering

No schema, endpoint or i18n change. The one API-visible change is a new `JobName` value, `S3FileMigrationQueueAll` (the S3 counterpart of upstream's `FileMigrationQueueAll`), which the OpenAPI spec and the TypeScript SDK list (the Dart client is generated at build time). The upgrade state is a fork `system_metadata` key, which `scripts/revert-to-immich.sql` deletes with the others (one line in step 0b); stock Immich reads its rows by key and never looks at it. `move_history` keeps Immich's meaning (a move in progress) and its rows are transient. Stock Immich cannot read S3 assets either way.

Upstream files: `storage-template.service.ts` loses its S3 skip and gains two calls in `getTemplatePath` and the per-part gate in `handleMigrationSingle` (an early return and a condition around the motion part's move); `storage.core.ts` swaps its early return for one call, and its `isAndroidMotionPath` body for one call into `s3-key.ts`; `storage.service.ts` hands its backend statics to the `storageBackends` registry, keeping four one-line delegates; `enum.ts` and `types.ts` take one registration line each for the derivative queue-all job and one each for `StorageTemplateS3State`; `user.service.ts`'s fork-owned S3 cleanup block takes its prefixes from one call into `storage-usage.ts`, which also decides the `library/` skip, so usage and deletion cannot drift apart. The trailing `/` on the template root, the destination check and its S3 error handling, the sidecar wait, the Migration-queue test, the upgrade state's decision and clear (`StorageTemplateS3Service`) and the gate's logic (`isManualOnlyTemplateMove`) all live in fork modules. Without S3 configured, upstream's disk behaviour changes in two places, neither on a path Immich writes: the trailing `/` (its guard now refuses a sibling folder), and `isAndroidMotionPath`, which now needs `encoded-video/` as a whole folder (see above); the gate reads nothing for a disk-only asset.

## Not covered

- Orphan detection on S3: integrity checks still skip S3 (open-noodle/gallery#685), so an object orphaned by step 5, by a replaced row or by a crash window is found only by hand.
- Edited derivatives (`isEdited`) are not re-pathed, as upstream.
- Multipart parts left by a server stopped mid-copy: removed only by a bucket lifecycle rule.
- A notice of the pending upgrade state outside the server log, such as on the storage template settings page (decision 1).
- With several microservices workers, an upload whose per-asset job another worker ran during the clearing run stays at its upload key until the next manual run.
- A clearing run whose S3 moves all fail still ends the wait (see the clear above).
